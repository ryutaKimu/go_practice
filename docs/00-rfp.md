## 1. 当社について

生活雑貨のオンライン販売事業者。自社ECサイトに加え、外部モール2社（楽天市場・Amazon）に出店している。
取扱SKU数は約12,000、1日あたりの注文件数は平常時2,000件、セール期は最大18,000件。
物流は自社倉庫1拠点＋3PL業者1社の計2拠点。

## 2. 現状と課題

現在は10年前に構築したPHPモノリスで受注・在庫を管理している。以下の課題がある。

1. **在庫の二重引当**
   自社ECとモールで在庫テーブルを別々に持っており、同期がバッチ（15分間隔）のため、
   セール時に「売り越し」が月20〜50件発生している。キャンセル対応の人件費が月80万円相当。

2. **注文状態の追跡が困難**
   注文ステータスがカラムの上書きで管理されており、いつ誰が何を変更したか追えない。
   顧客からの問い合わせ調査に1件あたり平均25分かかっている。

3. **外部連携のたびに本体改修が必要**
   モール追加やWMS（倉庫管理システム）連携のたびにモノリス本体を改修しており、
   小さな連携追加でもリードタイムが2ヶ月かかる。

4. **性能限界**
   セール開始直後に注文APIのレスポンスが10秒を超え、機会損失が発生している。

## 3. 本件で実現したいこと

在庫と注文を扱う**中核APIをGoで新規構築**し、既存モノリスから段階的に切り出す。
フロントエンドとして、社内オペレーター向けの**管理画面をReactで新規構築**する。

### スコープに含むもの

- 商品・SKUマスタの管理API
- 在庫の引当／引当解除／確定を含む在庫管理API
- 注文の受付・状態遷移・キャンセルを扱う注文API
- 社内オペレーター向け管理画面（商品一覧、在庫調整、注文検索・詳細、出荷指示）
- 既存モノリスからの初期データ移行
- 監視・ログ・アラートを含む運用設計と、6ヶ月間の運用保守

### スコープに含まないもの

- 顧客向けECサイトのフロントエンド（既存を継続利用し、APIのみ差し替える）
- 決済代行サービスとの接続（既存モノリスが引き続き担当する）
- 会計システム連携（次フェーズ）
- モール側の出品管理機能

## 4. 必須要件

| ID | 要件 |
| --- | --- |
| R-01 | 在庫の売り越しをゼロにすること。同一SKUへの同時注文でも整合性を保つこと |
| R-02 | 注文・在庫のすべての状態変更を、変更者・日時・理由とともに追跡できること |
| R-03 | 注文受付APIは、ピーク時（毎秒50リクエスト）でp95が300ms以内 |
| R-04 | 新しい販売チャネルの追加が、本体改修なしで設定のみで行えること |
| R-05 | 既存モノリスと並行稼働できること。段階的な切り替えが可能であること |

## 5. 提案に含めていただきたい事項

- システム構成図とアーキテクチャの方針
- 開発体制とスケジュール
- 移行計画（並行稼働から完全切替まで）
- 運用保守の体制と対応時間（想定：平日9-18時、障害時は24時間一次対応）
- 見積内訳

## 6. 制約事項

- インフラはAWSを利用中。ECS Fargate + Aurora PostgreSQL を想定
- 社内に運用を引き継ぐため、Go・React・PostgreSQL 以外の新規技術導入は事前協議とする
- 個人情報（氏名・住所・電話番号）を扱うため、アクセスログの保全が必要
