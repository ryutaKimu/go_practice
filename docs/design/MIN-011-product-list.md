# MIN-011: 商品一覧・検索 API — 設計判断

FR-103。クライアント確認の結果（2026-09-02 回答）と設計判断をまとめる。
API契約の正は [api/openapi.yaml](../../api/openapi.yaml)。

## クライアント回答で確定したこと

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| O-4（全SKU販売停止の商品） | **案B: 警告併記** | 「販売中に見えるのに注文が通らない」の調査コスト削減が刷新動機の一つ。案Cは商品が消えたと誤解される。詳細は [01-requirements.md](../01-requirements.md) 7章 |
| 商品名の一致方法 | 部分一致 | オペレーターは断片（「バスマット」）で探す。前方一致だとブランド名付き商品が探せない |
| SKUコードの一致方法 | 前方一致 | 業務は伝票コピペの完全一致で成立。前方一致はその上位互換でインデックスも効く |
| カテゴリ指定 | `categoryId`（UUID）+ 子孫カテゴリを含む | 「キッチン用品」で配下の「保存容器」等も出るのが期待。階層は2〜3層・総数100弱 |
| カテゴリ一覧API | `GET /categories` を追加（FR-107として要件に追記） | プルダウン用。当初仕様の抜け。**登録・編集・削除はフェーズ1スコープ外**（改廃は年数回・運用対応） |
| ページネーション | `{"page", "perPage", "total"}`。**total 必須** | 総件数を見て絞り込みを追加する使い方をする。以降の一覧APIの前例とする |

## API設計の判断

- **0件は正常系。** 200 で空の `items` + `pagination` を返す。404 は単体取得専用
- `categoryId` が UUID 形式として不正 → 400 VALIDATION_ERROR（既存 `mapError` の経路）。
  形式は正しいが存在しない → 検索条件としては成立しているので 200 で0件
- レスポンスは `id`（詳細画面への遷移キー）, `name`, `status`, `categoryName`, `hasActiveSku`,
  `createdAt`, `updatedAt`。カテゴリ名は categories を1回 JOIN して取得
- **返さないもの**: `description`（ペイロード肥大。詳細API=MIN-012の責務）、
  価格・SKU情報（SKU集約が重い。同上）、在庫数（FR-104の責務）

### hasActiveSku（O-4 案B の実現）

「販売可能な（active な）SKU が1件以上あるか」を返す。
`status: active` かつ `hasActiveSku: false` の商品に、管理画面が「販売可能なSKUなし」警告を出す。

- フィールド名に `available` を使わない。ユビキタス言語で「引当可能数 = Available」と衝突するため
  （[02-domain-model.md](../02-domain-model.md) 6章）
- 1ページ50件に対する SKU status の集約が必要。N+1 にせず EXISTS のサブクエリ or
  一括集約で取り、p95 500ms（NFR-02）を負荷試験で確認する
- **縮退案（クライアント合意済み）**: p95 500ms に収まらない場合、警告を一覧から外し
  詳細画面（MIN-012）のみに移してよい

## 性能の見立て

- 商品数は数千件規模（SKU約12,000）。商品名の部分一致は ILIKE '%…%' でインデックスが
  効かないが、この規模なら seq scan でも成立する見込み。超えたら再相談（pg_trgm 等）
- `total` の COUNT(*) は検索条件込みで別クエリ。同じく p95 500ms とセットで測る
- SKUコード前方一致は `skus.code` の既存インデックスで足りる（text_pattern_ops の要否は実測で判断）
- 子孫カテゴリ解決は WITH RECURSIVE。カテゴリ総数100弱・2〜3階層なので誤差
