### レビューでの指摘と学び

**指摘1: 条件式が `&&` になっていた**

```go
// 誤: 3つとも間違っていないと失敗しない
if item.OnHand != 20 && item.Reserved != 5 && item.Available() != 15 {

// 正: どれか1つでも間違っていれば失敗する
if item.OnHand != 20 || item.Reserved != 5 || item.Available() != 15 {
```

`Receive` にわざとバグ（`qty + 1`）を入れて実演したところ、
`&&` 版はPASSし、既存の `TestReceive` はFAILした。
**通っているのに何も検証していないテスト**だった。

得られた原則:

> テストが通ることは正しさの証明にならない。
> **バグを入れたら落ちることまで確認して、初めてテストが機能していると言える。**

MIN-021（50並列で売り越しゼロを検証）では、この確認が特に重要になる。
並行テストは「テスト自体が壊れていても、たまたま通る」ことがあるため。

**指摘2: 失敗メッセージの期待値が古いままだった**

失敗メッセージは失敗時にしか読まれないため、誤りに気づきにくい。
そこが間違っていると障害調査で混乱する。

**指摘3: テスト名が「何をするか」になっていた**

`TestReceiveAndReserve` → `TestInventory_入荷した分は引当できる`。
`CLAUDE.md` の規約どおり、「何を保証するか」を日本語で書く。
