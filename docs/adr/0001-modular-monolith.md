# ADR-0001: モジュラーモノリスで構築し、マイクロサービス化しない

- ステータス: 採用
- 日付: 2026-05-25
- 関連要件: R-01, R-05（既存との並行稼働）, NFR-04（可用性99.9%）

## 背景

既存PHPモノリスから在庫・注文を切り出す。
「切り出す」以上、在庫サービスと注文サービスに分割するという案が提案段階で出た。

## 決定

**単一のGoアプリケーション（モジュラーモノリス）として構築する。**
在庫と注文はパッケージとして分離するが、同一プロセス・同一データベースで動かす。

## 理由

1. **在庫引当と注文作成が同一トランザクションで完結する必要がある。**
   分割するとSagaパターンによる補償トランザクションが必要になり、
   「注文は作られたが引当に失敗した」中間状態を扱うことになる。
   R-01（売り越しゼロ）を最優先する本件で、整合性を緩める理由がない。

2. **クライアントの運用体制。** 情報システム部5名に引き継ぐ前提（RFP 制約事項）。
   複数サービスの分散トレーシングやデプロイ順序管理を運用してもらうのは現実的でない。

3. **可用性の観点でも有利。** サービス間通信が増えるほど障害点が増える。
   99.9%を単一サービスで達成するほうが容易。

4. 現在の負荷（ピーク50 req/s）は単一プロセスで十分にさばける。
   スケールが必要になったらタスク数を増やせばよい（ステートレスなため）。

## 将来の分割に備えること

いつでも切り出せる状態は保つ。

- パッケージ間の依存を `usecase` 層経由に限定し、他パッケージの `domain` 型を直接参照しない
- ドメインイベント（`OrderPlaced` 等）の名前を先に定義しておく（[02-domain-model.md](../02-domain-model.md) 5章）
- テーブルの所有パッケージを明確にし、他パッケージのテーブルを直接SQLで触らない

## 見直しの条件

- 単一DBの書き込みがボトルネックになり、Writer のスケールアップで解決できなくなったとき
- チームが分かれ、デプロイ独立性が開発速度の制約になったとき
