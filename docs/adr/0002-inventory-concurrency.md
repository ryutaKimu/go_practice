# ADR-0002: 在庫引当の並行制御に悲観ロックを採用する

- ステータス: 採用
- 日付: 2026-05-28
- 関連要件: R-01（売り越しゼロ）, NFR-01（p95 300ms）, NFR-03

## 背景

現行システムの最大の問題は売り越し（月20〜50件）である。
セール開始直後、同一SKUに対して複数の注文が同時に到着する。
このとき「引当可能数を超えて引き当ててしまう」ことを、確実に防ぐ必要がある。

ピーク時の負荷は 50 req/s。ただし注文は多数のSKUに分散するため、
**同一SKUへの同時アクセス**が起きるのはセール対象の数十SKUに限られる。

## 選択肢

### A. 悲観ロック（`SELECT ... FOR UPDATE`）

対象の在庫行をトランザクション内でロックし、検証してから更新する。

- 利点: 実装が単純で、正しさが自明。リトライ処理が不要
- 欠点: 同一SKUへの同時リクエストが直列化する。ホットスポットで待ちが発生

### B. 楽観ロック（version カラム）

version を条件に UPDATE し、0件更新ならリトライする。

- 利点: ロック待ちがない
- 欠点: 競合が多いと**リトライが多発してかえって遅くなる**。セール時はまさに競合が多い場面
- 欠点: リトライ上限に達したときの扱いが複雑（ユーザーには在庫不足と区別がつかない）

### C. 条件付きUPDATE のみ（`WHERE on_hand - reserved >= $qty`）

ロックを取らず、UPDATE の WHERE 句で在庫を検証する。

- 利点: 最も高速。1文で完結する
- 欠点: **どのSKUが不足したかをレスポンスで返せない**。FR-301 のエラー詳細（どのSKUがいくつ足りないか）を満たせない
- 欠点: ビジネスルールがSQLに埋まり、`domain` 層が空洞化する

## 決定

**A（悲観ロック）を採用する。**

理由:

1. 競合するSKU数が限定的（セール対象の数十SKU）なので、直列化の影響範囲が狭い
2. 1トランザクションの実行時間は数ms程度。同一SKUに50 req/s が集中しても、待ち行列は十分さばける
3. リトライ機構を持たないぶん、性能の予測可能性が高い。p95の見積もりが立てやすい
4. 検証ロジックを `domain` 層に置ける。Cのようにルールが散らない

`inventory_items.version` カラムは残す。将来Bへ切り替える余地と、
更新回数のデバッグ情報として有用なため。

## 実装上の必須事項

1. **ロック順序を `inventory_items.id` の昇順に固定する。** デッドロック回避のため必須
2. トランザクション内で外部API呼び出しを行わない（ロック保持時間を最小にする）
3. `statement_timeout` を 3秒に設定し、想定外の長時間ロックを防ぐ
4. DB側の `CHECK (reserved <= on_hand)` を最後の防波堤として残す

## 検証方法

`backend/internal/usecase/place_order_concurrency_test.go` にて、
在庫10のSKUに対し 3個ずつの注文を50並列で実行し、
**成功が正確に3件、`reserved` が9、失敗が47件** であることを検証する。

## 見直しの条件

負荷試験で以下のいずれかに該当した場合、Bを再検討する。

- 単一SKUへの同時引当で p95 が 300ms を超える
- ロック待ちタイムアウトが発生する
