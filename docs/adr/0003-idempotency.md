# ADR-0003: 注文登録の冪等性を一意制約違反の捕捉で実装する

- ステータス: 採用
- 日付: 2026-05-30
- 関連要件: FR-302

## 背景

注文登録APIは、ECサイトとモール連携バッチの両方から呼ばれる。
ネットワークタイムアウト時にクライアントが再送するため、
**同じ注文が二重に作られない**保証が要る。二重注文は二重引当を招き、R-01に直結する。

クライアントは `Idempotency-Key` ヘッダに一意な値（UUID）を付けて送る。

## 選択肢

### A. 事前チェック（SELECT してから INSERT）

```go
if existing := repo.FindByIdempotencyKey(key); existing != nil {
    return existing
}
return repo.Create(order)
```

- 欠点: **チェックと INSERT の間に競合する。** 同時再送で二重作成が起きる。
  まさに防ぎたい事象を防げない

### B. 一意制約違反を捕捉する

`orders.idempotency_key` に UNIQUE 制約を張り、INSERT が制約違反したら既存を返す。

```go
order, err := repo.Create(ctx, newOrder)
if isUniqueViolation(err, "orders_idempotency_key_key") {
    return repo.FindByIdempotencyKey(ctx, key)   // 初回の結果を返す
}
```

- 利点: DBの一意制約が競合を裁くので、どれだけ同時に来ても1件しか作られない
- 欠点: エラーを制御フローに使うため、一見わかりにくい

### C. 専用の冪等キーテーブルにレスポンスごと保存する

リクエストハッシュとレスポンスJSONを別テーブルに保存する（Stripe方式）。

- 利点: 注文以外のAPIにも汎用的に使える。異なるボディでの同一キー再送を検出できる
- 欠点: フェーズ1で冪等性が要るのは注文登録のみ。テーブルとTTL管理の運用コストに見合わない

## 決定

**B を採用する。**

競合安全性が構造的に保証されるのが決め手。Aは実装が素直に見えて、実際には要件を満たさない。

## 実装上の必須事項

1. `Idempotency-Key` ヘッダが無い場合は **400 を返す**（勝手にUUIDを生成しない）。
   生成してしまうと再送が別注文になり、冪等性が意味を失う
2. 既存注文を返すときも **HTTP 201 を返す**。クライアントから見て初回と同じ結果になる
3. レスポンスヘッダ `Idempotent-Replay: true` を付け、再送であることを観測可能にする
4. 一意制約違反の判定は、pgx の `*pgconn.PgError` の `Code == "23505"` かつ
   **制約名が `orders_idempotency_key_key` であること**を確認する。
   他の一意制約（`order_number` など）の違反を冪等と誤認しないため

## 未対応の論点

同一キーで**異なる内容**のリクエストが来た場合、現状は初回の注文を返す。
本来は 422 を返すべきだが、リクエストハッシュの保持が必要になる（選択肢C）。
運用で問題が出たらCへ移行する。それまでは、キー重複かつ内容相違を検知したらログに警告を出す。
